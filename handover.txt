  - v4 DOES preserve commas / periods / question marks / colons correctly when

1. Project Goal
---------------

Build a production-quality Arabic tashkeel (diacritization) system for
shipping as a commercial product.

Tashkeel = adding the 8 Arabic diacritic marks (U+064B..U+0652 + U+0670) to
unvowelized Arabic text without changing any letters. It is a character-level
sequence-labeling problem (not a free-form generation task).

Core model:
  CATT (Character-based Arabic Tashkeel Transformer) by Abjad AI.
  Encoder-only variant (EO), ~11M params, Apache 2.0, trained in plain
  PyTorch + PyTorch Lightning (NOT an LLM - Unsloth/GGUF/llama.cpp do NOT
  apply here).

Why CATT EO:
  - Paper baseline: 5.43% DER on WikiNews (ED) / ~similar on EO
  - Small, fast, shippable
  - Fully open Apache 2.0
  - We fine-tune it on our own data

What we tested and discarded:
  - Qwen 2.5 1.5B LLM fine-tune (Unsloth) - explored early, not the path
  - CATT ED (encoder-decoder) - trained, evaluated, LOST to EO on the real
    stratified eval. Abandoned.

by the balanced builders (which duplicate rows per-source to fix class imbalance).

D. datasets/arabic_tashkeel/catt_format_balanced_v3/
     327,769 train / 16,898 val / 16,898 test
     Built by scripts/data_prep/prepare_balanced_catt_training_data_v3.py
     Multipliers (evidence-tuned from the stratified 50/source eval):
       parquet:wikipedia  10x   (still weakest; push harder than v1's 6x)
       parquet:shamela     4x   (keep v2 level)
       quran               7x   (v1 proven; avoid over-boost -> regression risk)
       ambiguous_tier1     2x
       ambiguous_tier2     3x
       ambiguous_tier10    2x
       easyarabicnews_v1   2x + chunks  (NEW source)
       long_passages_v1    1x + chunks
       ambiguous_bonus     1x   (REGRESSED under oversampling in v1 - do NOT repeat)
       all others          1x
     Chunk sources produce an extra 6,698 overlapping chunks.
     Current promoted model was trained here.

Key insight from experiments:
  Pushing multipliers past ~12x gives diminishing returns. For wikipedia,
  even 12x barely moved DER because the real problem is OOD foreign
  transliterations, not lack of repetition. For shamela and quran,
  oversampling helped but capped out around 4-7x.

Important semantic:

  new training run that happens to initialize from the best prior weights.
  Epoch 0 should already be near the balanced_v1 best numbers because the
  weights are identical; subsequent epochs are where improvement (or
  regression) can happen.

  - ~18 min per epoch

11. Known Gotchas
-----------------

1. PowerShell quoting
   Paths with spaces need quotes. Use the call operator & when running an exe
   directly by path:
     & "C:\Users\Mohanad Dwekat\.unsloth\studio\unsloth_studio\Scripts\python.exe" script.py
   Bash-style escapes like C:/Users/Mohanad\ Dwekat/... DO NOT work in PowerShell.

2. Batch size 32 OOMs on 5070 Ti
   BATCH_SIZE=16 is the confirmed working setting. 32 crashes. Do not raise.

3. Windows DataLoader stability
   NUM_WORKERS=2 is the confirmed working setting. Higher counts intermittently
   hang. Keep low.

3b. VRAM spillover into Windows "shared GPU memory" on v3 is EXPECTED and
    NOT a problem.
    During balanced_v3 training we observed:
      - Dedicated GPU memory: 16/16 GB (pinned full)
      - Shared GPU memory:    ~9 GB (paged to system RAM)
      - Throughput:           stable at ~17 it/s (no degradation)
    Root cause: v3 has ~23% more long rows (> 768 chars) than v1. Since
    TashkeelDataset sorts by length, batches at the end of each epoch hit
    higher peak seqlens. Attention memory scales as O(batch * seqlen^2), so
    these peaks push the PyTorch CUDA caching allocator past 16 GB once and
    then it holds onto that allocation for the rest of the run.
    Windows 11 + recent NVIDIA drivers silently page the overflow into
    system RAM instead of throwing OOM. Performance cost is negligible
    because the long-row batches are rare (~0.16% of all batches).
    If a future run REALLY needs less VRAM, drop MAX_SEQ_LEN to 768 in
    catt_finetune.py. This truncates 0.16% of rows (mostly duplicated full
    passages) and drops peak VRAM by roughly 30%. For training runs that
    are hitting this ceiling but have stable throughput, it is not worth it.

4. Old OOM-after-OOM gotcha (legacy, was on RunPod)
   When a training run OOMs, the next run may OOM immediately on start because
   GPU memory isn't fully released. Fix: restart the Python process fully.
   Less of an issue locally since Python exits cleanly.

5. find_start_checkpoint() auto-detection
   The function in catt_finetune.py picks starting weights in this order:
     1. external/catt/catt_eo_ft_balanced_v3/catt_eo_ft_best.pt
     2. external/catt/catt_eo_ft_balanced_v1/catt_eo_ft_best.pt
     3. Latest .ckpt in catt_eo_ft_balanced_v3/ or catt_eo_ft_balanced_v1/
     4. Latest .ckpt in catt_eo_ft_v1/
     5. Released pretrained
   If you want to start a controlled comparison from v1 or from released
   pretrained weights, pass or hardcode that checkpoint explicitly.

6. Trainer does NOT resume - it starts fresh
   trainer.fit(...) without ckpt_path means the optimizer + epoch counter are
   reset. We load weights via load_state_dict, which keeps the model params
   but treats the run as new. If you want literal resume (continue optimizer
   state, advance past the saved epoch), pass ckpt_path=... to fit().
   We don't want that for dataset-change runs.

7. Canonical JSONL eval row count has grown
   Original eval:           16,220 rows
   After long_passages_v1:  16,601 rows
   After easyarabicnews_v1: 16,898 rows
   Any "before vs after" DER comparison must account for this. Handover section
   3 numbers (full eval 1.76% DER) were on the 16,601-row eval, not the 16,898.
   For apples-to-apples comparison after v3 training, re-run the stratified
   50/source eval (since it equally weights sources, not rows).

8. CATT clean_text() / punctuation handling
   The upstream v3-side TashkeelDataset calls tokenizer.clean_text() which
   strips everything outside the Arabic letter + diacritic + shaddah +
   ligatures + space set. Punctuation, digits, latin chars all get removed as
   spaces there, so the v3 model never sees them.
   The separate v4 punctuation-aware track changed this behavior and keeps
   punctuation in the tokenizer/input stream. However, the shared DER/WER eval
   workflow still mainly aligns by Arabic letters, which is why a separate
   punctuation audit was needed for v4.

9. ED was worse than EO
   Don't waste time retrying ED. The encoder-decoder variant was slower AND
   had higher DER than EO on our real eval. EO is the path.

10. Long passages still need special QA
    Short 10-20 word sentences often look nearly perfect, but long passages
    produce more accumulated tashkeel errors. Use debug_tools/tashkeel_web_ui.py
    to generate output and debug_tools/tashkeel_compare_ui.py to paste the
    model output against the cleaned golden fixture. The comparator reports
    both total tashkeel differences and a no-final-case-ending view.
